# Alternative: "the sheet is the app" (proposal)

Status: proposal, 2026-11-12, for a decision before Phase 4.

## Why reconsider

After Phases 0–3 the Python solution works on the test copy, but it costs ~2,200 lines of code,
~780 lines of tests and ~770 lines of docs, plus a service account, keys in a cloud environment and
an IMAP route that the cloud blocks. That is a lot for a three-person team to understand, and only a
programmer can change it.

Where the complexity comes from:

| Cause | Code it forces | Share |
|---|---|---|
| The automation edits a sheet that humans maintain by hand (formulas vary, rows move, month separators, hidden columns, typos) | header checks, formula/text-cell detection, re-matching rows, MASTER row, locale handling, `no-op`/`zero` rules | ~40% |
| It runs outside Google | service account, org policy exception, key handling, IMAP vs. Gmail API, cloud environment | ~20% |
| An LLM sits in the critical path, even for machine-generated reports | mail → JSON files → extraction files → schema validation → dedup of LLM output | ~25% |
| Intermediate state lives in files (`work/`) and several helper tabs | importers, run reports, plan files | rest |

The first and third causes are design choices, not necessities.

## The idea

**Don't automate the spreadsheet; make the spreadsheet the automation's home.**

1. **Numbers go into a new append-only tab, not into the overview.**
   Tab `Meldungen`: one row per reported number:
   `eingegangen | report_datum | termin | artist | anbieter | verkauft | quelle (link to the mail) | status`.
   The overview columns Dice/CTS/TT/Band pick up the latest number per show and provider with a formula
   (`=MAXIFS(...)` or a `QUERY`). The automation **never edits a cell a human edits**.
   - History is automatic, since `Meldungen` *is* the history. No snapshot job, no archive columns, and growth is a formula.
   - A correction is a new row with `quelle = manuell`, or `status = ignorieren` on a wrong one. Nothing is overwritten, and everything is traceable.
   - Formula cells, moving rows, separators and the MASTER row stop mattering for the import.

2. **Parse what machines send, deterministically. Hand everything else to a person.**
   Dice (CSV), Tickettoaster (HTML table) and Eventim are generated by systems in a fixed format. A
   15–30 line parser per provider reads them exactly. Anything a parser doesn't recognize, like an
   agency's band-shop mail, lands in `Meldungen` as `status = prüfen` with a link to the mail, and Tim types the
   number. That's one or two mails a week. No LLM in the weekly loop: predictable, free, and no mail
   content passes through an AI service (GDPR).

3. **Run it inside Google: Apps Script bound to the sheet.**
   - A menu in the sheet: *Friendly Reminder → Reports einlesen / Wochenmails vorbereiten / Neue Show anlegen*.
   - Time triggers (e.g. Monday 10:00, Tuesday 12:00) do the same without anyone clicking.
   - `GmailApp` reads the report label and creates real drafts in the mailbox (`createDraft`). Tim sees
     them where he already works.
   - No service account, no keys, no IMAP, no cloud environment, no org-policy exception.
   - Log: a `Protokoll` tab in plain German ("Mo 10:02 – Tickettoaster-Report vom 09.11.: 19 Shows, 1 neue Zahl, 1 zur Prüfung").

4. **Intake via a Google Form** (Phase 4).
   Dennis or Sönke fill in a form; required fields and formats are validated by the form itself. On submit, the script
   creates the Drive folders, inserts the show row from the MASTER row, and prepares the venue and archive drafts.

5. **Calendar via a shared Google Calendar** that Apple Calendar subscribes to, instead of `.ics` attachments.
   Events appear on their own.

6. **Claude builds and maintains it, but isn't in the loop.**
   The script lives in GitHub (`clasp`), and Claude Code edits it like any code. Claude is also useful
   on demand ("look at the `prüfen` rows and suggest numbers", "draft the agency reminder more politely"),
   but nothing breaks when it isn't there.

### How small it gets

Tickettoaster, as a sketch:

```js
function parseTickettoaster(html) {                 // the report is an HTML table
  const rows = [];
  for (const tr of html.split(/<tr/i).slice(1)) {
    const c = tr.split(/<t[dh][^>]*>/i).slice(1).map(s => s.replace(/<[^>]+>/g, '').trim());
    const m = (c[0] || '').match(/^(.*), (.*), (\d\d\.\d\d\.\d{4})$/);   // "Artist, Venue, 18.04.2027"
    if (m) rows.push({artist: m[1], venue: m[2], termin: m[3], verkauft: Number(c[4])});
  }
  return rows;
}
```

Dice: `Utilities.parseCsv(attachment.getDataAsString())` → event name, date, "Total Tickets Sold".

Estimated size for Phases 1–3: **~300–400 lines of Apps Script**, plus a handful of formulas.

## Comparison

| | Python + Claude (now) | Sheet-native (proposal) |
|---|---|---|
| Where it runs | cloud routine or a laptop | inside Google, next to the data |
| Credentials | service account key, mailbox password | none (runs as the mailbox owner) |
| Who can follow it | a programmer | anyone who opens the sheet: tabs, menu, `Protokoll` |
| Every number traceable | in `log` | in `Meldungen`, with a link to the source mail |
| Changes to the overview | written into cells, guarded by code | formulas only; humans keep their cells |
| History and growth | separate snapshot job | automatic |
| Messy mails | Claude extracts, code validates | `prüfen` row, a person enters the number (Claude optional) |
| Drafts | `.eml` files, mailbox later | real Gmail drafts from day one |
| Tests | 110 unit tests | parsers testable with saved sample mails; the rest is visible in the sheet |
| Weak spots | many moving parts | provider format changes (visible as `prüfen`), Apps Script 6-min run limit, tied to a Google account |

## Preconditions and open questions

1. **Is ticketing@friendlyreminder.live a Google Workspace mailbox?** If yes, everything runs there. If
   not, a forwarding filter into a Google account (like today's `+tickets` test setup) is enough.
2. **Overview columns become formulas.** Tim no longer types numbers into AA/AC/AE/AG. He adds a
   `Meldungen` row instead, or uses a manual-entry form. Is that acceptable to him?
   - A gentler variant: keep the overview as is, and add a `Vorschläge` view with a checkbox and an "Übernehmen" button that copies approved numbers. That's more human control, but some cell-writing logic comes back.
3. **Who owns the script and triggers** (the Google account they run as)?

## What we keep from the Python work

The Python code becomes the reference implementation. What carries over:
- the rules we learned: venue aliases, no-op and zero handling, duplicate mails, the typo hint, the falling-number check;
- the email templates and the test mails;
- the open questions answered so far.

The test cases become the checklist for the new version.

## Suggested next step

A **one-day spike** on the test sheet:
- the `Meldungen` tab;
- the TT and Dice parsers in Apps Script, reading the `n8n` label;
- one overview column switched to a formula;
- one "Wochenmails vorbereiten" menu entry that creates real drafts in the test Gmail account.

Then decide with the team: continue sheet-native, or keep the Python pipeline.
